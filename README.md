# Append-Only Memory Protocol

一套面向长期陪伴型 AI 应用的追加式纯文本记忆档案方案。

核心思路：**记忆只追加、不覆盖；分层检索、按需加载；稳定前缀吃缓存，动态内容不堆积。**

目标是让本地大模型或 DSH 生态中的陪伴类应用，在多次会话、长时间跨度下仍能保持人格一致、记忆连续、成本可控，并且可以跨模型迁移。

## 为什么需要它

本地模型和多数陪伴类应用本身没有跨会话记忆。常见做法是把历史对话不断塞进上下文，但会带来三个问题：

- **聊久了会漂移**：历史原话越多，模型越容易模仿自己，而不是遵守初始设定。
- **越跑越贵**：上下文越堆越厚，输出 token 最贵，长期运行成本不可控。
- **换模型会丢档**：记忆如果散落在聊天记录里，更换模型或客户端后很难迁移。

## 与现有项目的关系

本方案不是替代 Mem0、Supermemory、DSH 记忆插件或向量数据库，而是一套面向本地、单人、长期陪伴场景的轻量记忆协议。它不依赖云端服务，也不绑定特定模型，重点解决人格一致、记忆可迁移和成本可预期问题。

和现有项目的主要区别：

- **Mem0 / Supermemory / memU**：偏"云端服务 + 向量检索"；本方案偏"本地纯文本 + 追加式档案 + 缓存成本约束"。
- **DSH 原生记忆机制**：依赖事件溯源日志、AGENTS.md、技能文件；本方案更像一套独立协议，不依赖 DSH 内部实现。
- **DSH 记忆插件（dsh-memory、dsh-mnemon 等）**：多用 SQLite、工具调用、自动召回；本方案强调"追加式、纯文本、可迁移、可手动运行"。
- **本地 Git/Wiki 记忆（ai-memory、OpenHuman 等）**：也强调本地文件和版本管理；本方案更聚焦"陪伴型 AI 的长期人格、世代摘要、输出闸门"。

## 核心机制

### 1. 追加式纯文本档案

记忆只追加，不覆盖。新内容用简短电报体记录，保留关键情绪、画面、结论，但不逐字保存完整对话。这样既能积累长期记忆，又不会让上下文被大量历史原话污染。

### 2. 分层检索通道

记忆分为三层：

| 层级 | 作用 | 是否常驻 |
|---|---|---|
| 世代摘要 | 记录长期形成的稳定印象 | 常驻 |
| 当前目录 | 编号 + 情绪词 + 短钩子 | 常驻 |
| 单条正文 | 具体回忆细节 | 按需加载 |

这样即使记忆条目越来越多，也不会一次性把大量内容塞进上下文。

### 3. 稳定前缀 + 动态注入

输入顺序固定为：

> 人格卡 → 约定与边界 → 世代摘要 → 目录 → 按需条目 → 用户输入

稳定部分放在最前面，有利于缓存命中；动态部分放在后面，只在需要时注入。

### 4. 输出闸门

记忆写入遵循三条规则：

- 每日最多新增少量条目；
- 使用电报体，不写长段；
- 不暴露内部数值，如编号、状态标签、亲密值等。

这能防止档案越写越厚，也能避免模型把内部机制说出口。

## 适用场景

- DSH 桌宠类应用
- 本地大模型陪伴应用
- 角色扮演对话系统
- 长期对话记忆增强插件
- 需要跨模型迁移的档案层

## 不适用场景

- 实时多用户聊天
- 高并发服务
- 需要强一致性的业务系统
- 依赖云端向量检索的场景

本方案面向本地、单人、长期运行的轻量记忆层。

## 实现建议

- 使用纯文本或 JSON 存储；
- 用 Git 做版本管理；
- 定期备份；
- 更换模型时先做迁移测试；
- 关闭自动摘要，避免覆盖原始档案；
- 不写入 API Key、账号、绝对路径等敏感信息。

## 风险与边界

- 本方案只解决记忆层问题，不提升模型本身能力。
- 人格稳定性仍受模型指令遵循能力影响。
- 若执行环境不支持动态注入，自动检索会退化为手动。
- 二创形象、隐私数据、投稿条款需要单独处理。
- 想法本身不受著作权保护，可保护的是具体文档和实现。
